# 1. 验证动态场景与现有导航基线

> 本章不写新算法。你要先证明“待检测对象、传感器输入和导航对照组”都真实存在。否则以后看到错误结果时，无法判断问题在感知代码还是仿真环境。

## 1.1 本阶段的交付与通过条件

完成本章后，你应拥有一份简短的运行记录，并能独立证明下面四件事：

1. Gazebo 场景与机器人能启动。
2. `/scan`、`/odom`、`/tf` 正常发布。
3. 三个动态 actor 启动后在 RViz/Gazebo 中移动，且它们会被 LiDAR 实际扫到。
4. AMCL + DWB 静态导航 baseline 可接收目标并导航；它是未来 MPPI 结果的对照组。

本章不要求你解释每行 launch 文件，也不要求修改它。目标是能读懂系统输入输出。

## 1.2 必须理解的概念

### ROS 2 的最小心智模型

将 ROS 2 想成一组独立进程（节点）通过命名通道通信：

- **Node（节点）**：一个职责明确的程序。例如 Gazebo bridge、动态 actor 控制器、以后你写的感知节点。
- **Topic（话题）**：连续数据流。例如 `/scan` 每秒发布多帧激光数据。
- **Message（消息）**：话题上每一帧数据的类型。例如 `sensor_msgs/msg/LaserScan`。
- **Service（服务）**：一次请求—一次响应。例如控制 actor start/stop/reset。
- **Launch file**：一次性启动多个节点、设定参数和 remapping 的 Python 文件。
- **TF**：坐标系之间随时间变化的变换图；不是普通位置 topic。

### 本项目当前话题的职责

| 接口 | 类型/方向 | 含义 | 未来你的模块是否可用 |
| --- | --- | --- | --- |
| `/scan` | `LaserScan`，输入 | 机器人当前看到的 2D LiDAR 极坐标距离 | 是，感知的主输入 |
| `/odom` | `Odometry`，输入 | 仿真机器人位姿/速度估计 | 是，辅助理解自车运动 |
| `/tf`、`/tf_static` | TF，输入 | `odom → base_footprint → lidar_link` 坐标关系 | 是，感知变换必须使用 |
| `/cmd_vel` | `Twist`，Nav2 输出 | Nav2 希望机器人执行的速度 | 不直接用作检测输入 |
| `/cmd_vel_safe` | `Twist`，安全层输出 | 当前临时 scan safety guard 后的速度 | 不属于未来预测算法 |
| `/dynamic_obstacle/ground_truth_marker` | `Marker`，调试输出 | Gazebo 知道 actor 的真实位置 | **禁止作为算法输入** |

### 为什么必须禁止使用真值 Marker

如果你的 C++ 节点订阅真值 Marker，它当然能“完美知道”障碍物位置和速度，但这没有使用机器人传感器，也无法迁移到真机。它只能帮助你回答一个调试问题：**我从 `/scan` 检测到的位置是否大致落在 Gazebo 真值方框附近？**

## 1.4 启动“仅动态场景”

此模式只验证 Gazebo、bridge、传感器、actor 和 RViz，不启动 AMCL/DWB。终端 A：

```bash
cd /home/aderfd/PREDICTIVENAV2
source /opt/ros/jazzy/setup.bash
source install/setup.bash
ros2 launch predictive_nav_simulation dynamic_navigation_lab.launch.py \
  enable_dynamic_obstacle:=true
```

等待 Gazebo 与 RViz 出现。`enable_dynamic_obstacle:=true` 会启动三个确定性往返运动的方块：

| actor | 路径 | 速度 |
| --- | --- | --- |
| `dynamic_obstacle_actor` | `(2.25, -3.70)` ↔ `(2.25, -2.00)` | `0.35 m/s` |
| `dynamic_obstacle_center_actor` | `(-1.60, 0.00)` ↔ `(1.20, 0.00)` | `0.30 m/s` |
| `dynamic_obstacle_upper_actor` | `(2.20, 2.20)` ↔ `(5.40, 2.20)` | `0.28 m/s` |

### 在 RViz 中观察什么

- 红色激光点：真实的 `/scan` 测距结果。它会命中墙、家具、机器人可见的 actor。
- 橙色半透明方框：`/dynamic_obstacle/ground_truth_marker`，由 Gazebo actor 控制器发布。
- 两者不必每一帧精确重合：激光只扫到物体表面，并受角分辨率、遮挡和时间差影响。
- 合理现象是：actor 位于 LiDAR 可见范围时，红色点会贴近其可见边缘；actor 被墙遮挡时，红点可能完全看不见它。

## 1.5 用命令验证核心接口

保持终端 A 的 launch 运行，另开终端 B：

```bash
cd /home/aderfd/PREDICTIVENAV2
source /opt/ros/jazzy/setup.bash
source install/setup.bash
```

### 检查话题存在

```bash
ros2 topic list | rg '^/(clock|scan|odom|tf|tf_static|cmd_vel|cmd_vel_safe)$'
ros2 topic list | rg dynamic_obstacle
```

至少应看到 `/clock`、`/scan`、`/odom`、`/tf`、`/tf_static`、`/cmd_vel_safe` 和真值 Marker 话题。

> 如果你的系统没有 `rg`，将 `rg` 替换为 `grep`。

### 检查消息类型和频率

```bash
ros2 topic info /scan -v
ros2 topic hz /scan
```

`/scan` 的发布频率应接近 10 Hz。按 `Ctrl+C` 停止 `ros2 topic hz`。偶发小波动不表示错误；持续为 0 或命令一直无输出才需要排查。

读取一帧 scan 的头部和量程配置：

```bash
ros2 topic echo --once /scan
```

你会看到类似字段：

```yaml
header:
  stamp: ...
  frame_id: lidar_link
angle_min: ...
angle_increment: ...
range_min: ...
range_max: ...
ranges: [...]
```

现在只需知道：`ranges[i]` 是第 `i` 条激光的距离，真正的角度和坐标转换留给第 3 章。

### 检查 TF 是否持续变化

```bash
ros2 run tf2_ros tf2_echo odom base_footprint
```

机器人不动时数值可稳定；移动机器人时，平移或旋转会变化。按 `Ctrl+C` 停止。

再检查 LiDAR 的固定安装变换：

```bash
ros2 run tf2_ros tf2_echo base_link lidar_link
```

它应保持固定。若命令报坐标系不存在，不要猜 frame 名；先运行：

```bash
ros2 topic echo --once /scan --field header.frame_id
```

并将完整输出记录下来。

## 1.6 验证 actor 控制服务（可选但推荐）

controller 默认会自动开始运动。你可列出服务：

```bash
ros2 service list | rg dynamic_obstacle
```

通常会看到类似：

```text
/dynamic_obstacle_controller/start
/dynamic_obstacle_controller/stop
/dynamic_obstacle_controller/reset
```

暂停和恢复下方 actor：

```bash
ros2 service call /dynamic_obstacle_controller/stop std_srvs/srv/Trigger '{}'
ros2 service call /dynamic_obstacle_controller/start std_srvs/srv/Trigger '{}'
```

这是理解“可重复场景”的工具，不是未来算法依赖。你以后 benchmark 时会用 reset 确保每次实验从相同位置开始。

停止第 1.4 节的 launch（终端 A 按 `Ctrl+C`）后，再启动：

```bash

source /opt/ros/jazzy/setup.bash
source install/setup.bash
ros2 launch predictive_nav_bringup nav_baseline.launch.py
```

等待终端中 lifecycle manager 出现所有管理节点已 active 的信息。然后在 RViz 工具栏选择 **Nav2 Goal**，在地图的可通行区域单击目标点并拖出朝向。机器人应规划并运动。

此时不要启用动态 actor：本步骤的目的只是验证 DWB 的静态对照组。动态 actor 与 DWB/MPPI 的完整对比留到第 7 和第 9 章。

如果 RViz 中点击目标没有反应，检查：

```bash
ros2 action list | rg navigate_to_pose
ros2 lifecycle get /controller_server
```

预期可看到 `/navigate_to_pose` 和 `active`。若还未 active，请先等启动完成，不要反复点击目标。

## 1.8 常见错误和正确判断

| 现象 | 常见误解 | 正确判断/下一步 |
| --- | --- | --- |
| Gazebo 有方块但 RViz 没红点 | “LiDAR 坏了” | 先检查 actor 是否在激光可见区域，是否被墙遮挡，再看 `/scan`。 |
| 橙框移动、红点不完全贴合 | “检测一定错误” | 还没有检测；红点是物体表面，橙框是真值体积。第 4 章会输出自己的 cluster Marker。 |
| `/scan` 有数据但不知道 actor 的点是哪几个 | “需要读真值 Marker 做输入” | 不需要。第 3、4 章通过坐标变换、过滤和聚类从全部 scan 中提取观测。 |
| DWB 已经避开当前障碍 | “预测系统没有意义” | DWB 主要依据当前 costmap；你的目标是用未来位置与不确定性让 MPPI 更早地风险规避。 |
| 启动 Nav2 后 TF 混乱 | “可以同时加 world→odom” | AMCL 已知地图模式只能由 AMCL 负责 `map→odom`；不要额外添加 `world→odom`。 |
