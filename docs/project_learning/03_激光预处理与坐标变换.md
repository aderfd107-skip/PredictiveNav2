# 3. 激光预处理与坐标变换

> 第 2 章证明你能可靠地收到 scan；本章将它变成可用于跟踪的二维点。完成后，所有有效点都处在 `odom` 坐标系并带有原始 scan 时间戳。

## 3.1 本阶段交付

在 `predictive_nav_perception` 中新增 `scan_preprocessor_node`。它执行：

```text
LaserScan(/scan, lidar_link, stamp=t)
  → 验证 range、剔除无效/过近点
  → 极坐标转换为 lidar_link 的 (x, y)
  → 查询时刻 t 的 odom ← lidar_link TF
  → 得到 odom 中的 (x, y)
  → 发布 POINTS 类型 Marker，供 RViz 检查
```

本章输出仍然只是“预处理后的点集合”，不是 cluster，更不是动态目标。墙、静态家具和 actor 都会出现在点集合中，这是正常的。

## 3.2 为什么 tracking 不能直接在 `lidar_link` 中做

假设真实障碍物静止在走廊里，而机器人向前移动 1 米：

- 在 `lidar_link` 中，障碍物看起来向后移动约 1 米。
- 在 `odom` 中，静止障碍物应大致不动。

如果在 `lidar_link` 中估计速度，你会把自己的运动错当成障碍物的运动。`odom` 是本项目在线局部跟踪的连续参考系：Gazebo odometry 使它平滑连续。`map` 虽是全局坐标，但 AMCL 会修正 `map → odom`，可能产生小跳变；首版不要在 `map` 中估速。

本项目常见的 TF 关系是：

```text
map ──(AMCL，可能修正)──> odom ──(连续运动)──> base_footprint
                                                └──> base_link ──> lidar_link
```

目标变换写作 `odom ← lidar_link`，意思是“把在 `lidar_link` 表示的点，表达为 `odom` 中的点”。

## 3.3 LaserScan 的数学：极坐标转直角坐标

对 `ranges` 的第 `i` 个元素：

\[
\theta_i = angle\_min + i \cdot angle\_increment
\]

\[
x_i = r_i \cos(\theta_i),\qquad y_i = r_i \sin(\theta_i)
\]

其中 `(x_i, y_i)` 还在 `lidar_link`。不要假设 `i=0` 是正前方；唯一可信的来源是消息的 `angle_min` 与 `angle_increment`。

### 手算练习

令 `angle_min = 0`、`angle_increment = π/2`、ranges 为 `[2, 3]`：

- 第 0 点应接近 `(2, 0)`。
- 第 1 点应接近 `(0, 3)`。

先自己算，再用 `std::cos`、`std::sin` 验证。浮点数不能直接比较相等；测试中使用接近判断，如 `EXPECT_NEAR(value, expected, 1e-9)`。

## 3.4 本章新增的 C++ 知识

### 用 `struct` 表示简单数据

`Point2D` 只是两个数，没有复杂不变量，因此使用 `struct` 很合适：

```cpp
struct Point2D
{
  double x{0.0};
  double y{0.0};
};
```

`struct` 默认成员是 `public`；对纯数据这是清楚的。后面的 `KalmanTrack` 有状态、不变量和方法，会使用 `class` 与 `private`。

### `std::vector<Point2D>`

激光束数量由传感器配置决定，运行时才知道，因此使用动态数组 `std::vector`：

```cpp
std::vector<Point2D> points;
points.reserve(scan.ranges.size());
points.push_back(Point2D{x, y});
```

- `reserve` 预先分配可能需要的容量，避免循环中多次扩容；它不改变 `size()`。
- `push_back` 追加一个元素，并使 `size()` 增加。
- 此处不使用 C 的固定数组，也不手动 `malloc/free`。

### 算法与 ROS 节点分离

`scan_to_lidar_points()` 是纯函数：给定输入，永远得到相同输出，不读 topic、不查 TF、不打日志。它极易单元测试。

`ScanPreprocessorNode` 只负责 ROS 事务：收消息、查 TF、发布 Marker、记录诊断。将两者混在一个巨大 callback 中是初学者常见错误，会让测试和定位问题变得困难。

## 3.5 写可单测的 scan 几何函数

创建 `include/predictive_nav_perception/scan_geometry.hpp`：

```cpp
#pragma once

#include <vector>

#include <sensor_msgs/msg/laser_scan.hpp>

namespace predictive_nav_perception
{

struct Point2D
{
  double x{0.0};
  double y{0.0};
};

std::vector<Point2D> scan_to_lidar_points(
  const sensor_msgs::msg::LaserScan & scan,
  double extra_min_range_m);

}  // namespace predictive_nav_perception
```

参数 `extra_min_range_m` 是你额外保守的最小距离。例如传感器最小量程是 `0.05 m`，但希望忽略离 LiDAR 小于 `0.20 m` 的自体/噪声，则实际阈值是两者的较大值。

自己完成 `src/scan_geometry.cpp` 前，先列出逻辑：

```text
effective_min = max(scan.range_min, extra_min_range_m)
angle = scan.angle_min
遍历 range：
  如果 range 有限且 effective_min <= range <= scan.range_max：
      append {range*cos(angle), range*sin(angle)}
  angle += scan.angle_increment
返回 vector
```

参考实现：

```cpp
#include "predictive_nav_perception/scan_geometry.hpp"

#include <algorithm>
#include <cmath>

namespace predictive_nav_perception
{

std::vector<Point2D> scan_to_lidar_points(
  const sensor_msgs::msg::LaserScan & scan,
  const double extra_min_range_m)
{
  std::vector<Point2D> points;
  points.reserve(scan.ranges.size());

  const double effective_min = std::max(
    static_cast<double>(scan.range_min), extra_min_range_m);
  double angle = static_cast<double>(scan.angle_min);

  for (const float range : scan.ranges) {
    const double distance = static_cast<double>(range);
    if (std::isfinite(distance) &&
      distance >= effective_min && distance <= scan.range_max)
    {
      points.push_back(Point2D{
        distance * std::cos(angle), distance * std::sin(angle)});
    }
    angle += scan.angle_increment;
  }
  return points;
}

}  // namespace predictive_nav_perception
```

注意：无论某束 range 是否有效，角度都必须向前推进一次；它对应的是原始 scan 的位置，而不是“第几个有效点”。

## 3.6 为几何函数写测试

创建 `test/test_scan_geometry.cpp`。至少覆盖下面三类：

```cpp
TEST(ScanToLidarPoints, ConvertsAnglesToCartesianPoints)
{
  sensor_msgs::msg::LaserScan scan;
  scan.angle_min = 0.0F;
  scan.angle_increment = static_cast<float>(M_PI_2);
  scan.range_min = 0.01F;
  scan.range_max = 10.0F;
  scan.ranges = {2.0F, 3.0F};

  const auto points = predictive_nav_perception::scan_to_lidar_points(scan, 0.0);

  ASSERT_EQ(points.size(), 2U);
  EXPECT_NEAR(points[0].x, 2.0, 1e-9);
  EXPECT_NEAR(points[0].y, 0.0, 1e-9);
  EXPECT_NEAR(points[1].x, 0.0, 1e-9);
  EXPECT_NEAR(points[1].y, 3.0, 1e-9);
}
```

为了避免某些平台没有 `M_PI_2`，也可以在测试中定义 `constexpr double kHalfPi = 1.5707963267948966;`。再自己写：

1. 带 NaN 和 Inf 时，这两束不会出现在返回 vector。
2. `extra_min_range_m` 大于某束距离时，该点会被过滤。
3. 第一束无效、第二束有效时，第二束仍使用正确的原始角度。

## 3.7 TF：变换必须在消息的原始时间查询

假设 scan 是时间 `t` 采集的。机器人可能在 `t` 到 callback 执行的几十毫秒里移动。如果你取“最新的” `odom ← lidar_link`，就会把旧 scan 投影到新位置，产生拖影和假速度。

所以流程必须是：

```cpp
const auto stamp = rclcpp::Time(msg->header.stamp);
const auto transform = tf_buffer_.lookupTransform(
  target_frame_,             // "odom"
  msg->header.frame_id,      // 通常 "lidar_link"，不写死
  stamp,                     // 必须是 scan 的时间
  timeout);
```

如果变换不可用：**整帧丢弃、诊断计数、节流日志**。不要改用 `TimePointZero` 偷偷查最新 TF，也不要把 scan 当成已经在 odom 中。

## 3.8 编写预处理节点

此节点需要新增依赖：`geometry_msgs`、`tf2`、`tf2_ros`、`tf2_geometry_msgs`、`visualization_msgs`。在 `package.xml` 增加对应 `<depend>`，并在 `CMakeLists.txt` 增加 `find_package(...)` 与 `ament_target_dependencies(...)`。

节点类的成员顺序和构造方式如下：

```cpp
class ScanPreprocessorNode : public rclcpp::Node
{
public:
  ScanPreprocessorNode()
  : Node("scan_preprocessor_node"),
    tf_buffer_(get_clock()),
    tf_listener_(tf_buffer_)
  {
    target_frame_ = declare_parameter<std::string>("target_frame", "odom");
    extra_min_range_m_ = declare_parameter<double>("extra_min_range_m", 0.20);
    tf_timeout_s_ = declare_parameter<double>("tf_timeout_s", 0.05);

    marker_publisher_ = create_publisher<visualization_msgs::msg::Marker>(
      "~/preprocessed_points", 10);
    scan_subscription_ = create_subscription<sensor_msgs::msg::LaserScan>(
      "/scan", rclcpp::SensorDataQoS(),
      std::bind(&ScanPreprocessorNode::on_scan, this, std::placeholders::_1));
  }

private:
  tf2_ros::Buffer tf_buffer_;
  tf2_ros::TransformListener tf_listener_;
  // 其余 publisher、subscription、参数和计数成员由你补全。
};
```

这里要记住 C++ **成员按声明顺序初始化**，不是按初始化列表书写顺序。`tf_listener_` 依赖 `tf_buffer_`，所以 buffer 必须写在 listener 前面。

### 回调的正确骨架

```cpp
void on_scan(const sensor_msgs::msg::LaserScan::ConstSharedPtr msg)
{
  geometry_msgs::msg::TransformStamped odom_from_lidar;
  try {
    odom_from_lidar = tf_buffer_.lookupTransform(
      target_frame_, msg->header.frame_id, rclcpp::Time(msg->header.stamp),
      tf2::durationFromSec(tf_timeout_s_));
  } catch (const tf2::TransformException & ex) {
    ++dropped_tf_frames_;
    RCLCPP_WARN_THROTTLE(
      get_logger(), *get_clock(), 2000,
      "Dropping scan: cannot transform %s to %s: %s",
      msg->header.frame_id.c_str(), target_frame_.c_str(), ex.what());
    return;
  }

  const auto lidar_points = scan_to_lidar_points(*msg, extra_min_range_m_);
  std::vector<geometry_msgs::msg::Point> odom_points;
  odom_points.reserve(lidar_points.size());

  for (const auto & point : lidar_points) {
    geometry_msgs::msg::PointStamped input;
    input.header = msg->header;
    input.point.x = point.x;
    input.point.y = point.y;

    geometry_msgs::msg::PointStamped output;
    tf2::doTransform(input, output, odom_from_lidar);
    odom_points.push_back(output.point);
  }
  publish_marker(odom_points, msg->header.stamp);
}
```

`PointStamped` 的 header 必须和 scan 的 header 相同；不仅 frame 要是 `lidar_link`，stamp 也要是 scan stamp。`tf2::doTransform` 由 `tf2_geometry_msgs` 提供。

对应的源文件还需包含（除 ROS、消息头外）：

```cpp
#include <tf2/time.hpp>
#include <tf2_geometry_msgs/tf2_geometry_msgs.hpp>
#include <tf2_ros/buffer.h>
#include <tf2_ros/transform_listener.h>
```

首版逐点调用 `doTransform` 完全可以，因为 scan 约 10 Hz。以后若性能 profiling 证明它是瓶颈，再把 transform 转为 Eigen 并批量计算；不要现在为了“高级”而牺牲清晰和正确性。

### 发布 POINTS Marker

`publish_marker` 创建一个 `visualization_msgs::msg::Marker`：

```cpp
visualization_msgs::msg::Marker marker;
marker.header.frame_id = target_frame_;
marker.header.stamp = stamp;
marker.ns = "preprocessed_scan";
marker.id = 0;
marker.type = visualization_msgs::msg::Marker::POINTS;
marker.action = visualization_msgs::msg::Marker::ADD;
marker.pose.orientation.w = 1.0;
marker.scale.x = 0.04;
marker.scale.y = 0.04;
marker.color.r = 0.1F;
marker.color.g = 1.0F;
marker.color.b = 0.1F;
marker.color.a = 1.0F;
marker.points = odom_points;
marker_publisher_->publish(marker);
```

`POINTS` 的 `scale.x/y` 是点大小（米）。Marker topic 使用私有名 `~/preprocessed_points`，实际名称会是：

```text
/scan_preprocessor_node/preprocessed_points
```

在 RViz 添加一个 **Marker** display，topic 选择它，Fixed Frame 设为 `odom`。绿色点应与红色 scan 的几何形状一致，只是表达在固定的 odom 坐标中。

## 3.11 高频错误

| 现象 | 根因 | 修复方式 |
| --- | --- | --- |
| `Lookup would require extrapolation` | 用错时间、仿真时钟未启用或 TF 还没到 | 确认使用 `msg->header.stamp`、`use_sim_time:=true`；短暂失败应丢帧。 |
| Marker 固定在机器人身上 | Marker frame 仍是 `lidar_link`，或根本没有做 TF | Marker 使用 `odom`；检查 transform target/source 顺序。 |
| 绿色点旋转/平移方向怪异 | 查询成了 `lidar_link ← odom` 或 source frame 写死错误 | `lookupTransform(target=odom, source=msg->header.frame_id, ...)`。 |
| 有效点数量为 0 | `extra_min_range_m` 设得超过场景距离，或 `/scan` topic 错误 | 先用第 2 章诊断节点确认 range。 |
| callback 偶尔失败就程序退出 | 未捕获 `TransformException` | 只捕获并丢弃该帧，绝不能让感知节点崩溃。 |
